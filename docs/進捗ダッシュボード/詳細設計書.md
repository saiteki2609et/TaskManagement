### 0.2 実装時に判明した追加の注意点

基本設計・詳細設計の時点では想定していなかったが、実装・検証の過程で判明し、以降の実装で踏襲すべき注意点を以下にまとめる。

| 事象 | 原因 | 対応方針 |
| --- | --- | --- |
| プロジェクト切替時、`ProgressMatrixView`/`GanttView`/`QaView`が前のプロジェクトのデータを表示し続ける | これらは`useState(initialXxx)`でサーバーの初期データをコピーして保持するクライアントコンポーネントであり、URLクエリの変更(プロジェクト切替)でサーバー側の`initialXxx`は更新されるが、Reactは同一コンポーネントインスタンスを再利用するため内部stateは更新されない | `<ProgressMatrixView key={currentProjectId} ... />`のように、切替対象のprops(プロジェクトID)を`key`に指定し、切替時にコンポーネントを強制的に再マウントさせる(4.1節) |
| Base UIの`Select`で、値を`null`から後で文字列に変える(または`undefined`から定義済みの値に変える)と`Base UI: A component is changing the uncontrolled value state of Select to be controlled.`という警告が出る | Base UIはマウント時点の`value`が`undefined`かどうかで「非制御/制御」を判定するため、初期値`null`→`value={x ?? undefined}`という実装だと初回は`undefined`(非制御)、値が入ると定義済み(制御)に変わってしまう | `useState`の初期値を`null`ではなく`""`(空文字などプレースホルダを表す有効な値)にし、`value`には常に定義済みの値を渡す(`?? undefined`を書かない)。あわせて`items`propに選択肢の`{ label, value }`一覧を渡し、ポップアップを開かなくてもラベル解決できるようにする |
| ポップオーバーやダイアログを開いた直後にデータを取得する処理を、`if (id !== prevId) { setPrevId(id); fetch...().then(setState) }`のようなレンダー中の比較で実装すると、`Cannot update a component (...) while rendering a different component (...)`という警告が出ることがある | レンダー中のstate更新は原則安全だが、非同期取得(`fetch().then(setState)`)を伴う場合や、祖先にRouter等の外部コンテキストが絡む場合に、Reactの意図しないタイミングでの再レンダーを誘発することがある(Dialogの`open`propの初期化用途では問題にならないが、Popoverや動的取得を伴うケースで顕在化した) | データ取得を伴う初期化は、レンダー中の比較ではなく`onOpenChange`等の**実際のイベントハンドラ内**、またはクリックハンドラ内(親コンポーネント側)で行う(`AddFromMasterPopover`・`DesignDocumentPreviewDialog`で採用) |
| 再取り込み中に設計書一覧をポーリングしても、実行中のServer Action(`rescanDesignDocumentsAction`)が完了するまでポーリング用リクエストが1件も送信されない | Next.jsは同一クライアントからのServer Action呼び出しを直列化する(ネットワークログで実証済み) | ポーリング用途にはServer Actionではなく通常のRoute Handlerを新設し`fetch()`で呼ぶ(基本設計書 7.4節、3.5節) |
| dnd-kit(`useDraggable`/`useSortable`)を使うコンポーネントをSSRすると、`aria-describedby="DndDescribedBy-N"`のNがサーバー/クライアントで一致せずハイドレーションエラーになる | dnd-kitはmodule-levelのカウンタからこのidを採番するため、サーバー描画とクライアント初回描画でカウンタの状態が一致しない | dnd-kit依存のコンポーネント(`ProgressMatrixView`、`GanttView`、Todoの`SortableTaskList`)は`next/dynamic(..., { ssr: false })`でクライアント専用描画にする |
| `<table>`の直下(`<thead>`と`<tbody>`の間など)に`DndContext`を置くと、`<table>の子として<div>は不正>`という趣旨のハイドレーションエラーになる | `DndContext`はスクリーンリーダー向けの案内文を持つ非表示`<div>`(`id="DndDescribedBy-N"`)を子として追加で描画するため、`<table>`直下に置くとその`<div>`がテーブルの不正な子要素になる | `DndContext`は`<table>`を含む外側のコンテナ(例: `overflow-x-auto`のラッパーdiv)で囲み、`<table>`内部では`SortableContext`のみを使う(`SortableContext`はDOMを生成しないcontext providerのみなので`<thead>`と`<tbody>`の間に置いても問題ない)。`GanttView`の機能行D&D実装時に判明した(4.5節) |
| 上記のRoute Handlerを1秒間隔でポーリングする方式では、複数ファイルを再取り込みすると2件目以降の「更新中」表示が観測されないことがある | Ollamaのembeddingは1件目のみモデルロードで数秒〜数十秒かかるが、2件目以降は1秒未満で完了することが多く、ポーリング間隔より短い状態遷移を取りこぼす(DB側は正しく遷移しているが、クライアントが観測し損ねる) | ポーリングをやめ、状態変化のたびにプロセス内イベントバス(`progress-bus.ts`)へpublishし、Route HandlerがSSE(`ReadableStream`+`text/event-stream`)で即時pushする方式に変更する(3.7節) |
| `progress-bus.ts`のイベントバスをモジュール直下の変数(`const emitter = new EventEmitter()`)として実装すると、publish側(Server Action)とsubscribe側(Route Handler)でイベントが一切届かない | Next.jsの開発サーバーはRoute HandlerとServer Action/RSCを別のモジュールグラフとしてロードすることがあり、同一プロセス内でもそれぞれ独立したモジュールインスタンスが生成されてしまう | [prisma.ts](../../src/lib/prisma.ts)のPrismaClientシングルトンと同じ対処として、`globalThis`にインスタンスをぶら下げてプロセス全体で共有する(3.7節) |

### 1.1 Prismaスキーマ(実装用・確定版)

基本設計書 5.2節のドラフトを実装確定版とする(内容は同一のため、[schema.prisma](../../prisma/schema.prisma)への追記はそのまま用いる)。マイグレーションは以下の順に実施する。

```bash
# 1. schema.prisma に基本設計書 5.2節のモデルを追記
npx prisma migrate dev --name add_progress_dashboard_models
# 2. sqlite-vec拡張を使う場合のみ、生SQLで仮想テーブルを追加(1.3節)
npx prisma migrate dev --name add_document_chunk_vector_index --create-only
# → 生成された空マイグレーションファイルに1.3節のDDLを手書きし、migrate devで適用
```

- 既存の`Task`テーブルとは無関係のため、既存マイグレーション([prisma/migrations](../../prisma/migrations))には影響しない。
- `prisma/seed.js`は既存Todo用データのみを投入している。本機能用の初期データ(`GlobalDeliverableType`の初期セット等)投入が必要な場合は、`prisma/seed.js`に追記するのではなく、要否を実装着手時に確認する(初期マスタが空でもUIから追加できるため必須ではない。運用上あった方が親切、程度の位置づけ)。

### 1.3 ベクトル検索のDDL(sqlite-vec採用時)

基本設計書 7.3節の第一候補方針に基づき、`DocumentChunk.embedding`(`Bytes`)とは別に、ANN検索用の仮想テーブルを生SQLマイグレーションで追加する。

```sql
-- migration: add_document_chunk_vector_index
CREATE VIRTUAL TABLE IF NOT EXISTS document_chunk_vec USING vec0(
  chunk_id TEXT PRIMARY KEY,
  embedding FLOAT[768]  -- 採用embeddingモデルの次元数に合わせて実装時に確定
);
```

- アプリケーションからは`DocumentChunk`作成時に`document_chunk_vec`へも同じ`id`でINSERTし、削除時(`DesignDocument`のCascade削除)は`DocumentChunk`削除に追随して`document_chunk_vec`側も明示的に`DELETE`する(Prismaの`onDelete: Cascade`は仮想テーブルには効かないため、`deleteDesignDocumentInternal`相当の処理で両方削除する)。
- `sqlite-vec`拡張のロードに失敗する環境(ビルド不可等)を想定し、7章のRAG実装は「ベクトル検索アダプタ」インターフェースの背後に隠蔽し、フォールバック実装(全件コサイン類似度計算)に差し替え可能な構成とする(7.2節)。

### 2.2 集約ステータス・遅延判定(`src/components/dashboard/aggregate-status.ts`)

基本設計書 3.2節の関数を、実装可能な完全形として以下に確定する。

```typescript
import type { Deliverable, CellAggregateStatus } from "@/components/dashboard/types";

function startOfDay(date: Date): Date {
  return new Date(date.getFullYear(), date.getMonth(), date.getDate());
}

export function isDelayed(
  d: Pick<Deliverable, "status" | "plannedEndDate">,
  now: Date = new Date()
): boolean {
  if (d.status === "done") return false;
  if (!d.plannedEndDate) return false;
  return new Date(d.plannedEndDate).getTime() < startOfDay(now).getTime();
}

export function aggregateCellStatus(
  deliverables: Pick<Deliverable, "status" | "plannedEndDate">[],
  now: Date = new Date()
): CellAggregateStatus {
  if (deliverables.length === 0) return "not_applicable";
  if (deliverables.some((d) => isDelayed(d, now))) return "partially_delayed";
  if (deliverables.every((d) => d.status === "done")) return "done";
  if (deliverables.every((d) => d.status === "not_started")) return "not_started";
  return "in_progress";
}

export function countDelayed(
  deliverables: Pick<Deliverable, "status" | "plannedEndDate">[],
  now: Date = new Date()
): number {
  return deliverables.filter((d) => isDelayed(d, now)).length;
}

export function buildMatrix(
  features: { id: string; name: string; order: number }[],
  phases: { id: string; name: string; order: number }[],
  deliverables: Deliverable[],
  now: Date = new Date()
) {
  const sortedFeatures = [...features].sort((a, b) => a.order - b.order);
  const sortedPhases = [...phases].sort((a, b) => a.order - b.order);

  return sortedFeatures.map((feature) => ({
    feature,
    cells: sortedPhases.map((phase) => {
      const cellDeliverables = deliverables.filter(
        (d) => d.featureId === feature.id && d.phaseId === phase.id
      );
      return {
        phase,
        deliverables: cellDeliverables,
        status: aggregateCellStatus(cellDeliverables, now),
        doneCount: cellDeliverables.filter((d) => d.status === "done").length,
        totalCount: cellDeliverables.length,
      };
    }),
  }));
}

export function phaseCompletionSummary(
  phase: { id: string },
  deliverables: Deliverable[]
): { done: number; total: number } {
  const inPhase = deliverables.filter((d) => d.phaseId === phase.id);
  return { done: inPhase.filter((d) => d.status === "done").length, total: inPhase.length };
}

export function projectCompletionSummary(
  deliverables: Deliverable[]
): { done: number; total: number } {
  return { done: deliverables.filter((d) => d.status === "done").length, total: deliverables.length };
}
```

- `buildMatrix`はSCR-01の描画に直接使う中核関数。`ProgressMatrixView`はサーバーから渡された生データ(`features`, `phases`, `deliverables`)をこの関数に通すだけで表全体を組み立てる。
- `now`を引数化しているのはユニットテスト容易性のため(既存コードには同種のテスト容易性配慮は明示的には無いが、遅延判定は日付境界のテストが重要なため本機能では意図的に導入する)。

### 2.5 Server Actionのエラー表現方針

0.1節の方針に基づき、Server Actionの戻り値を2系統に分ける。

```typescript
// システムエラー(DB接続断など): 例外をthrow。クライアントはtry/catchで固定文言toastを出す(既存踏襲)

// 業務ルールエラー(利用者の操作次第で回避可能なもの): 戻り値の判別共用体で表現する
export type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: ActionError };

export type ActionError =
  | { code: "DUPLICATE_PROJECT_NAME"; message: string }
  | { code: "DELIVERABLE_TYPE_IN_USE"; message: string; count: number };
```

適用対象は以下の2箇所のみ(要件定義書上、動的な件数・文言が必須なもの)。それ以外の全Actionは既存踏襲で例外+固定文言toastとする(不要な複雑化を避けるため、業務ルールエラーの型を持つのはこの2種類に限定する)。

| Action | エラー種別 |
| --- | --- |
| `createProjectAction` / `updateProjectAction` / `restoreProjectAction` | `DUPLICATE_PROJECT_NAME` |
| `deleteDeliverableTypeAction` | `DELIVERABLE_TYPE_IN_USE` |

**D&D実装(dnd-kit)**:
- `DndContext`を`ProgressMatrixView`のルートに配置。`sensors`は`PointerSensor`(閾値`distance: 4`でクリックと誤認しないようにする)を使用。
- `DeliverableTypePalette`内の各バッジを`useDraggable({ id: type.id, data: { type } })`。
- `MatrixCell`を`useDroppable({ id: \`${feature.id}:${phase.id}\`, data: { featureId, phaseId } })`。
- `onDragEnd`ハンドラで以下を実行:
  1. ドロップ先が無効(`over === null`)なら何もしない
  2. `type.defaultPhaseId`とドロップ先`phaseId`が不一致の場合、`window.confirm`ではなくshadcnの`AlertDialog`を開き「想定工程(基本設計)と異なる列(詳細設計)にドロップしようとしています。追加しますか?」を表示。キャンセルで中断
  3. 対象セルに既に同一`typeId`の`Deliverable`が存在する場合、別の`AlertDialog`で「同じ種類の成果物が既に存在します。追加しますか?」を表示。キャンセルで中断(2と3の両方に該当する場合は2→3の順に連続表示)
  4. 上記を通過したら`createDeliverableFromDropAction`を呼び、成功時`setDeliverables(fresh)` + `toast.success`
- キーボード操作代替: `CellDetailPanel`内に`Select`(成果物種類を選択)+「追加」ボタンを常設し、同じ`createDeliverableFromDropAction`を呼ぶ(D&Dを経由しないため、工程不一致・重複チェックはこの経路でも同様に事前確認ダイアログを挟む)。

**`src/components/dashboard/gantt-date-scale.ts`(実装確定版)**:

```typescript
export type GanttUnit = "week" | "month";

export type GanttColumn = { label: string; offsetPx: number };   // 2段目(日)
export type GanttMonthLabel = { label: string; offsetPx: number }; // 1段目(月、月が変わる列にのみ生成)

export type GanttScale = {
  rangeStart: Date; rangeEnd: Date; pxPerDay: number; totalWidthPx: number;
  columns: GanttColumn[]; monthLabels: GanttMonthLabel[]; rangeLabel: string;
};

export function buildDateScale(unit: GanttUnit, anchor: Date): GanttScale;
// week: anchorを含む週(日曜始まり)の7日間、1日=64px
// month: anchorを含む暦月の全日、1日=28px
// columnsは日ごと(2段目のラベル)、monthLabelsは月が変わる列にのみ生成(1段目)
// rangeLabel: week="9/6 - 12"形式、month="2026年9月"形式(4.2節のページング見出しに使う)

export function shiftGanttAnchor(anchor: Date, unit: GanttUnit, direction: 1 | -1): Date;
// week: 7日単位でanchorを加減算
// month: anchorの月を+1/-1し、日を1日に固定(月末日の翌月加算による繰り上がりを避ける)
```

- 実装時に、要件定義書が当初想定していた「四半期表示・月表示は週単位の目盛り」を「週/月とも日単位の目盛り+2段ヘッダー(月/日)+ページング」に変更した。理由: 四半期表示は実運用上ほぼ使われず、月表示の「1週間ごとの目盛り」は日単位の粒度が欲しいという要望に対して不十分だったため、「表示範囲を1週間/1か月に絞り込む代わりに、その範囲内は必ず日単位で見せる」方式に一本化した(要件定義書 5.2節)。
- ページング操作(`handlePage(direction)`)は`setAnchor(prev => shiftGanttAnchor(prev, unit, direction))`のみで、データの再取得は行わない(`deliverables`は初期取得済みの全件をそのままクライアントで保持しており、`buildDateScale`が計算する表示ウィンドウが変わるだけ)。
- `GanttBar`は`position: absolute`で`left: dateToOffsetPx(...)`, `width: (endOffset - startOffset)`をpx指定。予定バー(背景・半透明)と実績バー(前景・塗り)を同一セル内に重ねる2層構造。表示ウィンドウ(`scale`の`rangeStart`〜`rangeEnd`)からはみ出す成果物のバーは、`left`/`width`の計算上ウィンドウ外の座標になるが、行コンテナ(`<div className="relative h-10 overflow-hidden">`)側で`overflow-hidden`を指定しているため、見た目上は表示範囲の境界で自動的に切り取られる(バー側に範囲外判定のロジックは持たせない)。
- バークリックで4.4節の成果物詳細編集画面(`DeliverableDetailDialog`)を開く(旧仕様のPopoverでの簡易表示は廃止済み)。
- 横軸の月・日ラベルは`<th>`の子要素として描画しているため、ブラウザ既定の`text-align: center`を継承してしまう。`text-left`を明示的に指定して左揃えにする(0.2節)。

**機能行のドラッグ&ドロップ並び替え**:

- `GanttFeatureRow`(機能行を1つ切り出した子コンポーネント)が`useSortable({ id: feature.id })`を呼ぶ。`sensors`は`ProgressMatrixView`・Todoの`SortableTaskList`と同じ`PointerSensor`(`activationConstraint: { distance: 4 }`)。
- ドラッグハンドル(`GripVertical`アイコン)は常時表示(Todoの並び替えハンドルと同じ方針。0.2節)。ハンドルの`onClick`は`e.stopPropagation()`し、行全体の`onClick`(展開/折りたたみtoggle)を誤発火させない。
- `DndContext`は`<table>`の外側(`overflow-x-auto`のラッパーdiv)に置き、`SortableContext`のみを`<table>`内(`<thead>`と`<tbody>`の間)に置く。理由は0.2節の新規追加ガチャ(`DndContext`を`<table>`直下に置くとアクセシビリティ用の非表示`<div>`がテーブルの不正な子要素になりハイドレーションエラーになる)を参照。
- `SortableContext`の`items`は現在画面に表示中の機能(`groups`、成果物が1件も無い機能はGanttビュー自体に表示されないため対象外)のidのみ。`onDragEnd`(`handleFeatureDragEnd`)は、表示中の機能同士の並び替えとして`over`/`active`のインデックスを解決し、非表示の機能(成果物0件、または他のフィルタで除外中)は元の相対位置を保ったまま全体の`features`配列にマージしてから`reorderFeaturesAction(projectId, orderedIds)`を呼ぶ。失敗時は`setFeatures`を並び替え前の配列に戻して`toast.error`。
- `Feature.order`は全体進捗ビューのマトリクス行の並び順とも共有されるフィールドのため、ガントビューで並び替えると次にマトリクス表を(再マウントを伴う形で)表示した際にも新しい順序が反映される。ただしタブ間でリアルタイムに同期はしない(各タブが独立した`features`のローカルコピーを持つため。0.2節の`key={currentProjectId}`と同じ制約の一種)。

### 5.2 チャンク分割(`src/lib/design-docs/chunk.ts`)

```typescript
export type Chunk = { sectionLabel: string; content: string; chunkIndex: number };

export function chunkText(
  sections: { label: string; text: string }[],
  options: { maxChars: number; overlapChars: number } = { maxChars: 800, overlapChars: 100 }
): Chunk[];
```

- セクション(見出し・シート・ページ)単位を最優先の分割境界とし、1セクションが`maxChars`を超える場合のみ文字数ベースでさらに分割する(`overlapChars`分を前チャンク末尾から持ち越し、文脈の連続性を保つ)。
- `maxChars`/`overlapChars`の具体値(800字/100字)は暫定値。採用embeddingモデルのコンテキスト長・応答品質検証後に調整する(基本設計書 10章の持ち越し事項)。

### 5.3 embedding生成・保存(`src/lib/design-docs/embed.ts` + `scan-folder.ts`)

```typescript
export async function scanAndIndex(projectId: string, folderPath: string): Promise<RescanResult> {
  // 1. folderPathを再帰的に走査し(walkDir)、対応拡張子(.md/.txt/.docx/.xlsx/.pdf)のファイル一覧を取得
  //    サブディレクトリの読み取りに個別に失敗しても(権限エラー等)、その配下だけをスキップして
  //    他のサブディレクトリの走査は継続する(1箇所の失敗で全体が中断されないようにする)
  // 2. projectId配下の既存DesignDocumentを全件取得し、レコードごとにfs.accessで実ファイルの
  //    存在を確認する。存在しなければ削除する(DocumentChunkはCascadeで削除。resultのremovedを加算し、
  //    publishDesignDocProgress(projectId)でSSE配信)。
  //    ※ 1.のtargetFilesとの単純な差分ではなくfs.accessで個別確認するのは、サブディレクトリ走査が
  //      一部失敗した場合に実在するファイルのレコードを誤って削除しないようにするため
  // 3. 各ファイルについて fileHash = sha256(ファイル内容) を算出
  // 4. 既存 DesignDocument(projectId, filePath)を検索
  //    - 存在せず or hash不一致 → 抽出・embedding処理の"前"に
  //      DesignDocumentをindexStatus="processing"でupsert(先行コミット) + publishDesignDocProgress
  //      → extractText → chunkText → 各チャンクをembed
  //      → DesignDocumentをindexStatus="indexed"でupdate + 既存DocumentChunkを全削除して作り直し
  //      → publishDesignDocProgress(基本設計書 7.4節。SSEでQaViewへ即時反映)
  //    - 存在してhash一致 → skip(processingの先行コミットも行わない。何も変更しない)
  //    - 抽出/embedding中に例外 → DesignDocumentをindexStatus="failed"で保存(またはupdate)、
  //      failuresに理由を追加して次のファイルへ + publishDesignDocProgress
  // 5. 集計結果(added/updated/skipped/failed/removed)を返す
}
```

- Ollama embeddings APIは`src/lib/llm/ollama-client.ts`の`embed(texts: string[]): Promise<number[][]>`経由で呼ぶ。
- `DocumentChunk.embedding`(`Bytes`)には、`Buffer.alloc` + `writeFloatLE`/`readFloatLE`で手動シリアライズした`Float32`配列を保存する(`src/lib/qa/embedding-codec.ts`の`encodeEmbedding`/`decodeEmbedding`)。`Float32Array.buffer`をそのまま使うとPrismaの`Bytes`型が要求する`Buffer<ArrayBuffer>`と型が合わない(`ArrayBufferLike`になる)ため、この手動実装を採用した。

## 7. 環境変数・設定

| 変数名 | 用途 | 既定値(開発時) |
| --- | --- | --- |
| `OLLAMA_HOST` | Ollama REST APIのベースURL | `http://localhost:11434` |

`.env`([.env](../../.env))に追記し、既存の`DATABASE_URL`と同様にNext.jsのサーバーサイド専用値として扱う(クライアントに公開しないため`NEXT_PUBLIC_`prefixは付けない)。

**モデル選定の経緯**: 対話モデルは当初`qwen3:4b`を評価したが、`"think": false`をリクエストに指定してもthinkingモードのタグ(`<think>...</think>`)を出力し続け、応答時間が68〜160秒程度とGPUなし・RAM8GB環境での実用性を満たさなかったため不採用とした。`gemma3:4b`はthinkingモードを持たず2〜7秒程度で応答し、参照情報に基づく回答・根拠なし時の拒否応答のいずれも正しく行えたため採用した。
