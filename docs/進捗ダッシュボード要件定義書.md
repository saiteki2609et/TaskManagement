# プロジェクト進捗管理画面 要件定義書

## 1. 目的・背景

- 本プロジェクト(TaskFlow)には個々のタスクを管理するTodo機能が既にあるが、これとは別に**プロジェクト全体の進捗**を俯瞰できる画面が存在しない。
- 本要件は、個別タスク/チケットの管理ではなく、**工程(フェーズ)と成果物の単位でプロジェクト全体の進み具合を可視化する**ことを目的とする。
- あわせて、蓄積された設計書を横断的に参照し、仕様に関する質問に根拠(参照元)付きで回答するAI機能(ローカルLLM)を追加する。

## 2. スコープ

### 2.1 対象(In Scope)

1. 機能(モジュール) × 工程の一覧をマトリクス表形式で表示し、各セルの集約ステータス(未着手/進行中/完了 等)を1画面で把握できる「全体進捗ビュー」(1セルには複数の成果物が紐づく)
2. 成果物を縦軸、日付を横軸にとり、各成果物の進捗と遅延状況を時系列で把握できる「スケジュール(ガント)ビュー」
3. 登録済みの全設計書を読み込んだうえで、仕様に関する質問にローカルLLMが回答し、根拠となった参照元(ドキュメント名・該当箇所)を提示する「設計書QA機能」
4. プロジェクトの新規作成・削除・アーカイブ、および共通成果物種類マスタの管理を行う「プロジェクト管理画面」

### 2.2 対象外(Out of Scope)

- 個々のタスク・チケットの作成/管理(既存のTodo機能の範囲であり、本機能では扱わない)
- 工数管理・要員アサイン管理
- 外部の課題管理ツール(Jira等)との連携
- 通知・アラート機能(遅延の自動通知など)は本フェーズでは対象外とし、画面上での可視化のみとする

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| プロジェクト | 進捗管理の最上位の管理単位。工程・機能・成果物種類マスタ・成果物・設計書はすべて特定の1プロジェクトに属し、画面上部の切替UIで対象プロジェクトを切り替えて利用する |
| 工程(フェーズ) | 要件定義・基本設計・詳細設計・実装・テスト等、プロジェクトの大きな作業区分。プロジェクトごとに定義可能とする |
| 機能(モジュール) | システムを構成する**サブシステム単位**の機能。例: ECサイトであれば「発注機能」「会員機能」「在庫管理機能」「決済機能」など。全体進捗ビューの行軸となる |
| 成果物(ドキュメント/納品物) | ある機能・ある工程において作成される具体的な成果物。例: 「発注機能 基本設計書」「発注機能 画面設計書」「発注機能 API仕様書」など。**1つの「機能×工程」の組み合わせに対して複数の成果物が存在しうる** |
| ステータス | 成果物ごとの進捗状態。「未着手」「進行中」「保留」「レビュー中」「完了」の5種とする |
| 遅延 | 予定完了日の翌日以降になってもステータスが「完了」になっていない、個々の成果物の状態(猶予日数は設けない。1日でも過ぎたら遅延とする) |
| 一部遅延 | 全体進捗ビューのセル(機能×工程)に紐づく成果物のうち、1件以上が「遅延」している状態。セルの集約ステータスとして独立に表示する |

## 4. 利用者・利用シーン

- 想定利用者: プロジェクトマネージャー、リーダー、プロジェクトメンバー
- 利用シーン: 定例会議での進捗確認、遅延している成果物の早期発見、仕様確認の効率化
- 複数プロジェクトを掛け持つ利用者向けに、画面上部にプロジェクト切替UI(セレクトボックス等)を設け、選択中のプロジェクトの工程・機能・成果物種類マスタ・進捗データ・設計書を切り替えて表示する
- 本アプリケーションはロールによる権限分離を設けない。**利用者(社内メンバーに加え、委託先等の社外関係者を含む)は全員同一の権限を持ち**、工程・機能・成果物種類マスタ(共通マスタ含む)を一覧画面から自由に追加/編集できるものとする(ただし成果物種類の削除は5.1節の制約に従う)

## 5. 機能要件

### 5.1 全体進捗ビュー(機能 × 工程マトリクス)

**目的**: プロジェクト全体の進捗を1画面でサマリ把握する。

**表示内容**:
- 表形式で、行に「機能(モジュール)」、列に「工程」を配置したマトリクス表
- 1セル(機能×工程)には**複数の成果物が紐づきうる**(例: 「発注機能」×「基本設計」セルには「発注機能 基本設計書」「発注機能 画面設計書」「発注機能 API仕様書」等が含まれる)
- 各セルには、そのセルに含まれる成果物群の**集約ステータス**を色分けアイコン・バッジ等で表示する。集約ルールは以下の優先順位で判定する:
  1. セル内に1件でも「遅延」(予定完了日を超過し、かつ未完了)の成果物がある → セルは **一部遅延**(最優先。赤色等で強調表示)
  2. 上記に該当せず、セル内の全成果物が「完了」→ セルは **完了**
  3. 上記に該当せず、セル内の全成果物が「未着手」→ セルは **未着手**
  4. 上記のいずれにも該当しない(進行中・保留・レビュー中が混在)→ セルは **進行中**
  5. セルに成果物が1件も登録されていない(0件)場合は「対象外(-)」として区別する
- セルには件数バッジも表示する(例: 「進行中(2/5)」で5件中2件完了等、内訳が一目でわかるようにする)
- 工程ごとの完了率(サマリ)をヘッダー等に表示(例: 「基本設計: 12/20 成果物 完了」)
- プロジェクト全体の完了率をヘッダーに表示

**操作**:
- 各セルをクリックすると、その機能×工程に紐づく**成果物の一覧がグリッド形式(カード/テーブルのグリッドレイアウト)でモーダル/サイドパネルに表示**される
  - グリッドの各項目には、成果物名・ステータス・担当者・予定日・実績日・メモ等を表示する
  - グリッド内から個別成果物のステータスを変更できる
  - グリッド内から成果物の編集・削除ができる
- 画面上には「成果物種類一覧」パレット(例: 基本設計書、詳細設計書、画面設計書、API仕様書、テスト仕様書、DB設計書 等)を常時表示し、**ユーザーは一覧から成果物種類をドラッグして、対象のセル(機能×工程)にドロップすることで成果物を追加**できる
  - ドロップすると、当該セル(機能×工程)に「[機能名] [成果物種類名]」を初期値とした成果物が1件追加され、ステータスは「未着手」となる。成果物名は追加後に編集可能とする
  - ドラッグ&ドロップ操作が行えない環境(キーボード操作・タッチ未対応端末等)向けに、セル詳細パネルからのプルダウン選択による追加も代替手段として提供する(アクセシビリティ対応)
  - パレット上の成果物種類には想定工程(例: 「基本設計書」は基本設計工程向け)を持たせ、ドロップ先の工程列と異なる場合は警告を表示する(誤配置防止)
  - 同一セルに、既に存在する成果物種類と同じ種類を再度ドロップした場合は「同じ種類の成果物が既に存在します。追加しますか?」等の確認ダイアログを表示し、**OKを押下した場合のみ重複して成果物を追加**する(キャンセルで追加を中止)
- 機能・工程・成果物種類のマスタ自体の追加/編集/削除ができる(ロール分けは設けず、プロジェクトメンバーなら誰でも操作可能)。これらのマスタは**プロジェクトごとに個別管理**され、あるプロジェクトでの変更が他プロジェクトに影響しない
- **既に1件以上の成果物(`Deliverable`)が紐づいている成果物種類(`DeliverableType`)は削除できない**。削除しようとした場合はエラーメッセージ(例: 「この種類を使用している成果物が◯件あるため削除できません」)を表示する。名称・想定工程の変更は紐づく成果物の有無に関わらず可能とする

**表示イメージ(マトリクス)**:

| 機能 \ 工程 | 要件定義 | 基本設計 | 詳細設計 | 実装 | テスト |
| --- | --- | --- | --- | --- | --- |
| 発注機能 | ✅完了(1/1) | 🔴一部遅延(2/3) | ⬜未着手(0/2) | - | - |
| 会員機能 | ✅完了(1/1) | ✅完了(3/3) | 🔵進行中(1/2) | - | - |
| 在庫管理機能 | 🔵進行中(1/2) | ⬜未着手(0/2) | - | - | - |

**セルクリック時のグリッド表示イメージ(例: 「発注機能」×「基本設計」)**:

| 成果物名 | ステータス | 担当者 | 予定完了日 | 実績完了日 |
| --- | --- | --- | --- | --- |
| 発注機能 基本設計書 | ✅完了 | 山田 | 2026-06-10 | 2026-06-09 |
| 発注機能 画面設計書 | 🔴進行中(遅延) | 佐藤 | 2026-06-15 | - |
| 発注機能 API仕様書 | 🟡レビュー中 | 佐藤 | 2026-06-18 | - |

### 5.2 スケジュール(ガント)ビュー(成果物 × 日付)

**目的**: 各成果物の進捗を時系列で把握し、遅延を視覚的に検知する。

**表示内容**:
- 縦軸に成果物を一覧表示、横軸に日付(週/月単位で切替可能)を配置
- 5.1と同様、成果物は機能単位で増加するため、縦軸は**機能(最上位階層)ごとにグルーピングして表示**する
- **初期表示では最上位階層(機能行)のみを表示し、配下の成果物行は折りたたんだ状態とする**。機能行をクリック(展開)すると、その機能配下の成果物行が表示される
- 各成果物について、予定期間(開始日〜完了予定日)をバーで表示
- 実績(実際の開始日・完了日、または現在の進捗率)を予定バーに重ねて表示し、両者を比較可能にする
- 本日時点で予定完了日を超過し、かつ未完了の成果物は「遅延」として強調表示(赤色等)する
- ステータス(未着手/進行中/保留/レビュー中/完了)に応じてバーの色を変える
- 機能行(折りたたみ時のサマリ行)には、配下の成果物のうち遅延しているものの件数を表示する(例: 「発注機能(遅延2件)」)

**操作**:
- 表示期間の切替(週/月/四半期)
- 成果物バーをクリックすると詳細(予定日・実績日・遅延日数等)を表示
- 機能・工程でのフィルタリング(特定機能/特定工程の成果物のみ表示)

### 5.3 設計書QA機能(ローカルLLM)

**目的**: プロジェクト内の設計書を横断的に検索し、仕様に関する質問に根拠付きで回答することで、仕様確認の工数を削減する。

**前提・方針**:
- 外部への情報送信を避けるため、LLMはローカル環境で動作するものを利用する(例: Ollama等でホストするオープンウェイトモデル)
- **GPUなし・RAM8GBのマシンでも動作すること**を必須要件とする。そのため、採用するLLMは軽量な量子化モデル(CPU推論可能なサイズ・量子化レベル)に限定する
- 設計書の取り込みは、プロジェクトごとに**ローカルフォルダのパスを指定**する方式とする(個別ファイルのアップロードは行わない)。フォルダの自動監視は行わず、**画面上の「再取り込み」ボタンを押下したタイミングでのみ**指定フォルダ配下をスキャンし、新規・更新ファイルを検出して取り込む
- 対応ファイル形式は、Markdown(.md)、Word(.docx)、Excel(.xlsx)、PDF(.pdf)、テキスト(.txt)を基本とし、その他の一般的なテキスト系ドキュメント形式も可能な範囲で対応する。**画像形式(png/jpg等)は対象外**とする
- 取り込んだファイルはテキスト抽出・チャンク分割・embedding化してベクトルストアに格納する(RAG方式)
- 質問に対しては、関連度の高いチャンクを検索してLLMのコンテキストに与え、回答を生成する

**表示・操作**:
- チャット形式のUIで質問を入力できる
- 回答本文に加え、**参照元(ドキュメント名・見出し/セクション・該当箇所へのリンク)を必ず併記**する
- 参照元をクリックすると該当ドキュメントの該当箇所を表示できる
- 未取り込み/インデックス未反映の設計書がある場合、その旨を画面上で警告表示する
- 「再取り込み」ボタンを押下すると、指定フォルダを再スキャンして未取り込み・更新ファイルをインデックスに反映する(実行中はローディング状態を表示する)
- 過去の質問履歴を一覧・再表示できる

**非対象**:
- 本機能はQ&A(参照・要約)に限定し、設計書の自動生成・自動修正は対象外とする
- 設計書フォルダの自動監視・定期的な自動再取り込みは対象外とする(再取り込みは手動トリガーのみ)

### 5.4 プロジェクト管理画面

**目的**: プロジェクト自体のライフサイクル管理、および全プロジェクト共通の成果物種類マスタを管理する。

**表示・操作**:
- プロジェクトの一覧表示(プロジェクト名、作成日、設計書フォルダパス、アーカイブ状態等)
- プロジェクトの新規作成(プロジェクト名・設計書フォルダパスを入力して作成。作成時に共通成果物種類マスタ(`GlobalDeliverableType`)の内容がプロジェクト固有マスタ(`DeliverableType`)へ初期コピーされる)
  - プロジェクト名は一意でなければならない。**論理削除により保持期間(30日)中のプロジェクトの名称も重複チェックの対象に含める**(削除済み・未削除を問わず、同名のプロジェクトは新規作成できない)。同名を指定した場合はエラーメッセージを表示する
- プロジェクトの編集(名称・設計書フォルダパスの変更。名称変更時も上記の一意性チェックを行う)
- プロジェクトのアーカイブ/アーカイブ解除(進捗ビュー等のプロジェクト切替候補から一時的に除外する。データは保持する)
- プロジェクトの削除は**論理削除**とし、関連する工程・機能・成果物・設計書インデックス・質問履歴等を含めて**削除から30日間保持**する。削除前に確認ダイアログを表示する
- 本画面内に**「ゴミ箱」タブ**を設ける(既存Todo機能のゴミ箱とは別。独立画面ではなく、プロジェクト管理画面内のタブ切り替えで表示する)。保持期間内(30日以内)のプロジェクトを一覧表示し、以下の操作ができる:
  - 復元(論理削除を取り消し、通常のプロジェクト一覧に戻す。復元時は現在有効なプロジェクトとの名称重複がないか再チェックする)
  - 完全削除(即時に物理削除する。**保持期間(30日)が経過しても自動での物理削除は行わず、完全削除は常にユーザーの手動操作を必須とする**)
  - 保持期間(削除からの経過日数、残り日数)を一覧上に表示する
- 共通成果物種類マスタ(`GlobalDeliverableType`)の一覧表示・追加/編集/削除(既存プロジェクトの`DeliverableType`には遡って影響しない。あくまで新規プロジェクト作成時のひな形として機能する)
- 本画面もロール分けは設けず、アプリの利用者であれば誰でも操作可能とする

## 6. 非機能要件

| 分類 | 要件 |
| --- | --- |
| セキュリティ | 設計書QA機能は社外秘情報を扱うため、外部APIへのデータ送信を行わない(ローカルLLM完結とする) |
| 性能 | 進捗ビュー・ガントビューは工程数・成果物数が数十〜百件程度でもストレスなく表示できること |
| 動作環境 | ローカルLLMを含め、GPUなし・RAM8GBのマシン上でも実用的な応答時間で動作すること |
| 保守性 | 工程・機能・成果物種類のマスタはUI上で追加/編集できること(コード修正不要) |
| マルチプロジェクト | 全てのマスタ・進捗データ・設計書はプロジェクト単位で分離され、あるプロジェクトのデータ変更が他プロジェクトに影響しないこと |
| 可用性 | ローカルLLMの推論には数秒〜数十秒かかる可能性があるため、回答生成中はローディング状態を明示する |
| 既存資産との整合 | 既存のNext.js(App Router) + TypeScript + Tailwind CSS + shadcn/ui + Prisma(SQLite)の構成を踏襲する |

## 7. データモデル(想定)

既存の`Task`モデル(Todo機能)とは独立した新規モデルとして定義する想定。`Project`を最上位に、他のエンティティは基本的に`projectId`で紐づく。

- `Project`(プロジェクト): id, name, designDocFolderPath(設計書取り込み対象のフォルダパス), isArchived, deletedAt(論理削除日時。Todo機能の`Task`と同様の論理削除方式), createdAt
  - 権限・ロールの概念は持たない(アプリ利用者は全員同一権限)
  - `deletedAt`が設定されたプロジェクトは**削除から30日間**保持され、期間内はプロジェクト管理画面内の「ゴミ箱」タブから復元・完全削除ができる。保持期間経過後の自動物理削除は行わず、完全削除は常に手動操作とする
  - `name`は**論理削除中のプロジェクトも含めて一意**とする(削除済み・未削除を問わず重複不可)
- `Phase`(工程): id, projectId, name, order
- `Feature`(機能): id, projectId, name, order
- `GlobalDeliverableType`(共通成果物種類マスタ): id, name, defaultPhaseName, order
  - 管理者が全プロジェクト共通のひな形として管理する固定マスタ
  - プロジェクト新規作成時に、この内容が当該プロジェクトの`DeliverableType`へ初期コピーされる
- `DeliverableType`(成果物種類マスタ・プロジェクト固有): id, projectId, name(例: 基本設計書、詳細設計書、画面設計書、API仕様書等), defaultPhaseId(想定工程。ドラッグ&ドロップ時の警告判定に使用), order
  - プロジェクト作成時に`GlobalDeliverableType`からコピーされたうえで、プロジェクトごとに自由に追加・編集できる
  - **1件以上の`Deliverable`から参照されている`DeliverableType`は削除不可**(アプリケーション層で制約。参照が0件になって初めて削除可能)
- `Deliverable`(成果物): id, projectId, name, featureId, phaseId, typeId(`DeliverableType`への参照。任意), assignee, plannedStartDate, plannedEndDate, actualStartDate, actualEndDate, status(未着手/進行中/保留/レビュー中/完了), progress(%), memo, order
  - 1つの`featureId` + `phaseId`の組み合わせに対して、`Deliverable`は複数件存在しうる(1:N)。同一`typeId`の重複も許可する
  - パレットから`DeliverableType`をセルにドラッグ&ドロップした際、`featureId`・`phaseId`・`typeId`を持つ`Deliverable`が1件生成される(`name`の初期値は「機能名 + 種類名」)
  - 全体進捗ビューのセル(機能×工程)の集約ステータスは、当該`featureId`・`phaseId`に紐づく`Deliverable`群の`status`・遅延有無から画面表示時に動的に算出する(5.1節の集約ルールを参照。DBには保持しない)
- `DesignDocument`(設計書): id, projectId, title, filePath, updatedAt, インデックス化状態
- `DocumentChunk`(QA用): id, documentId, content, embedding, sectionLabel(参照元表示用)
- `QaHistory`(質問履歴): id, projectId, question, answer, sources(参照ドキュメント一覧), createdAt

> 注: `Deliverable`の`status`は`plannedEndDate`と現在日時の比較により、画面表示時に「遅延」フラグを動的に算出する(DBに保持しない想定)。

## 8. 技術方針(たたき台)

- フロントエンド/バックエンド: 既存踏襲(Next.js App Router, Prisma, SQLite)
- ガントビュー: 既存UIライブラリ(shadcn/ui)ベースで独自実装、または軽量な日付グリッドコンポーネントを採用
- 全体進捗ビューのドラッグ&ドロップ: dnd-kit等の既存ライブラリの採用を検討
- ローカルLLM: Ollama等によるホスティングを想定。GPUなし・RAM8GBでの動作を必須とするため、**CPU推論可能な小型量子化モデル(数B〜Nパラメータクラス、4bit量子化等)** に限定する。具体的な採用モデルは実装フェーズでリサーチ・検証のうえ決定する
- 設計書取り込み: 画面上の「再取り込み」ボタン押下をトリガーに、指定フォルダ配下を走査する(自動監視は行わない)。ファイル種別ごとにテキスト抽出処理を分岐(例: Markdown/テキストはそのまま、Wordは`mammoth`、Excelは`xlsx`、PDFは`pdf-parse`等のライブラリ想定)
- ベクトル検索: SQLiteベースの構成を維持する場合は`sqlite-vec`等の拡張、または別途軽量ベクトルストアを検討

## 9. 確定事項(2026-09-07 回答済み)

| 項目 | 決定内容 |
| --- | --- |
| 工程・成果物マスタの管理単位 | 複数プロジェクトを切り替えて管理する(8章「プロジェクト」参照) |
| ステータスの選択肢 | 「未着手/進行中/保留/レビュー中/完了」の5種とする |
| 予定日・実績日の入力方法 | 手動入力とする |
| 設計書の取り込み方式 | フォルダパスを指定する方式とする(アップロードは不要) |
| ローカルLLMの実行環境 | GPUなし・RAM8GBでも動作すること |
| 対応する設計書のファイル形式 | .md, Word, Excel, PDF, テキスト等、読み取り可能な形式一通り。画像形式は対象外 |
| 「機能(モジュール)」の分割粒度 | サブシステム単位とする |
| セルの集約ステータス表示ルール | 「一部遅延」を独立した集約ステータスとして表示する(5.1節参照) |
| ガントビューの初期表示 | 最上位階層(機能行)のみ表示し、配下の成果物行は折りたたむ |
| 成果物種類マスタの管理方法 | プロジェクトごとにカスタマイズ可能。プロジェクト作成時に使用する共通の固定マスタ(`GlobalDeliverableType`)も別途管理者が管理する |
| 同一セルへの重複ドラッグ&ドロップ | 確認ダイアログを表示し、OK押下で重複追加を許可する |
| ローカルLLMの採用モデル | 実装フェーズでリサーチのうえ決定する(GPUなし・RAM8GB動作の制約は必須要件として維持) |
| `GlobalDeliverableType`の編集権限 | 本アプリはロールによる権限分離を設けない。共通マスタ・プロジェクト固有マスタとも、利用者であれば誰でも一覧画面から編集できる |
| プロジェクトの新規作成・削除・アーカイブ | 5.4節「プロジェクト管理画面」として機能要件に追加した |
| 「遅延」判定の猶予日数 | 猶予日数は設けない。予定完了日を1日でも過ぎたら「遅延」とする |
| 設計書フォルダの再スキャンタイミング | 自動監視は行わず、画面上の「再取り込み」ボタン押下による手動トリガーのみとする |
| プロジェクト削除時の関連データの扱い | 完全削除ではなく、論理削除により一定期間保持する(既存Todo機能の論理削除・ゴミ箱方式を踏襲。5.4節参照) |
| 成果物種類マスタの名称変更・削除時の扱い | 1件以上の成果物が紐づく成果物種類は削除禁止とする(名称変更は可能) |
| 社外関係者への権限付与 | 社内メンバーと同一の権限でよい(ロール分けなしの方針を維持) |
| プロジェクトの論理削除データの保持期間 | 削除から30日間保持する。保持期間経過後の自動物理削除は行わず、完全削除は常に手動操作とする |
| プロジェクトのゴミ箱画面 | 既存Todo機能のゴミ箱とは別に、**プロジェクト専用のゴミ箱**を設ける(5.4節参照) |
| プロジェクト名の一意性制約 | 論理削除中(保持期間30日以内)のプロジェクトも含めて名称は一意とし、同名での新規作成は不可とする |
| プロジェクト専用ゴミ箱の設置場所 | 独立画面ではなく、**プロジェクト管理画面内のタブ**として設置する |
